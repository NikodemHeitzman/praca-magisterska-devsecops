# 2026-11-13: akceptacja modelu pull zamiast OIDC (zmiana protokołu v1)

- **Uczestnicy:** autor pracy, promotor (dr inż. Stanisław Lota)
- **Forma:** korespondencja e-mail. Pytanie autora wysłane 2026-11-11, odpowiedź promotora z 2026-11-13. Notatkę spisał agent (Claude Code) 2026-11-13 na podstawie treści wiadomości przekazanej przez autora.
- **Zadanie:** E05-06
- **Materiał:** [ADR-0032](../adr/0032-potok-bez-poswiadczen-aws-wdrozenie-pull.md), [dziennik 2026-11-11, Sesja 7](../log/2026-11-11.md)

## Pytanie autora (streszczenie)

- SCP zarządzana przez AWS dla kont z rejestracji „Sign up for AWS (new)” blokuje tworzenie dostawców tożsamości (`iam:*Provider*`), więc federacja OIDC GitHub Actions → AWS jest na tym koncie niewykonalna. Ograniczenie znosi tylko nieodwracalne przejście na plan płatny bez limitu wydatków.
- Zamiast tego potok nie ma poświadczeń AWS, a instancja sama pobiera wskazaną wersję obrazu (model pull). Integralność wdrożenia zależy od łańcucha dostaw obrazu (do opisania w 5.3).
- Zmiana dotyka zamrożonego protokołu v1: K8 („rola OIDC”, 5.1) i zabezpieczenia w sekcji 6, punkt 4. Na pomiary H1 i H2 nie wpływa.
- Pytanie: akceptacja zmiany albo przejście na plan płatny z zachowaniem OIDC.

## Ustalenia

- **Promotor akceptuje zmianę.** Model pull zostaje, plan płatny odpada.
- **Promotor prosi, żeby problemy z kontem opisać w pracy:** SCP z `RegionFloor` (ADR-0030) i blokadę dostawców tożsamości (ADR-0032). Miejsca w tekście: 4.2 (realizacja infrastruktury), 5.3 (ograniczenia) i rekomendacje dla małych zespołów.

## Do zrobienia

- Zamknięcie E05-06 ze zmienionym zakresem: z kryteriów spełnione jest tylko „brak `AWS_ACCESS_KEY_ID` w sekretach”, a dwa kryteria dotyczące OIDC zastępuje ADR-0032.
- E05-07: mechanizm modelu pull z osobnym ADR.
